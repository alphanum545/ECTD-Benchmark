# Optimization log

Every change to a scheduling policy, with the reason it should work, the
measurement that decides it, and the decision. Generated by
`scripts/render_optimizations.py` from `registry.json` and the benchmark
artifact; do not edit by hand.

The rule this document exists to enforce: **a change is not an optimization
until it has a mechanism and a measurement, and the measurement agrees with
the mechanism.** An entry whose claim the artifact contradicts fails the
build rather than being quietly softened in the prose.

## The scoring rule these changes act on

`_place_scored` picks a processor by minimising

```
score = start + self_weight * w[task][q] + tail[task][q]
```

because it computes `eft = start + w[task][q]` and then adds the tail on
top. `self_weight = 1` is stock ECTD. Every scoring change below is a
statement about `self_weight` or about `tail`, which is why they are
comparable rather than being unrelated tweaks.

## Accepted

### `own_cost` — Weight the task's own execution cost twice in the processor score

**Status:** ACCEPTED  
**Kind:** algorithm

**Measured:** `v:own_cost` = 1368.61 pooled, -6.67% vs `ECTD`, -0.90% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

`_place_scored` scores a candidate processor as `eft + tail`, where `eft` is `start + w[task][q]` and the tail is the optimistic cost of everything AFTER the task. So the score is `start + 1*w + continuation`.

This variant scores `eft + (w + continuation)`, which is `start + 2*w + continuation`. The task's own execution cost is counted twice.

That is not a correction of an error. Stock ECTD's estimator is already the unbiased one: `start + w + continuation` is the actual finish time of this task plus the estimated cost of what follows. Counting `w` twice is a deliberate bias toward the processor where THIS task runs fastest, at the expense of the tail estimate.

It helps because the tail estimate is the unreliable half of the score. The optimistic cost table assumes every successor lands on its best processor and that no contention occurs, which is systematically optimistic once several tasks compete for the same processors. The own-cost term is concrete and known. Weighting it up trades a noisy forecast for a certain local cost, and on this corpus that trade pays.

**Claim before measuring:** At least 1% better than stock ECTD pooled, and not worse than AEFT.

**Measured outcome:** Measured at least 1% faster than stock ECTD pooled.

**Decision.**

Accepted. Largest single improvement measured on this corpus, and the only change that beats AEFT pooled. The mechanism above is the reason to believe it generalises rather than being a corpus artifact: it is a bias toward measured cost over estimated cost, which should pay wherever the tail estimate is optimistic.

The value 2 is now measured as a plateau, not a lucky point. The sweep in scripts/ectd_search.py scores self_weight from 0.0 to 3.0 on a 282-instance stratified sample (one instance from every family x level x processor cell). The curve is smooth and single-peaked: 0.0 is catastrophic (+57.3% vs stock), 0.5 is +12.5%, 1.0 is stock, 1.5 is -4.4%, 2.0 is -5.45%, 3.0 is -4.0%. 2.0 sits at the top of a broad basin, with 1.5 and 3.0 both within 1.5 points. That shape is what a real effect looks like; a lucky point would not have smooth neighbours on both sides.

self_weight = 0.0 is worth keeping in mind as a sanity check on the whole harness: it means ignore the task's own cost entirely and place purely on start + tail, and it is 57% worse than stock. The own-cost term is doing real work, not decoration.

**Evidence:** `docs/benchmark/summary.json (ablation run 45799615516, 2094 instances)`; `scripts/ectd_search.py sweep, 282-instance stratified sample`

### `own_cost_damped` — Damp only the tail, not the task's own measured cost

**Status:** ACCEPTED  
**Kind:** algorithm

**Measured:** `v:own_cost_damped` = 1366.94 pooled, -6.78% vs `ECTD`, -1.02% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

own_cost sets the score to `start + w + (w + continuation)`, counting the task's own execution cost twice. The damping multiplier from the author code was then dropped, because at self_weight 1.0 it is worth only 0.12% and the first ablation measured the undamped version as marginally better.

That was the wrong conclusion from a real measurement. Damping is not worthless; it was being applied to the wrong thing. The multiplier exists to correct an over-optimistic tail estimate. The task's own execution cost is measured, not estimated, so there is nothing optimistic about it to correct. Damping the whole own-cost tail therefore damps a quantity that does not need it, which is why its benefit appeared to vanish as self_weight rose.

This variant multiplies only the continuation by the damping weights and leaves the own cost alone: `tail = w + continuation * weights`. The correction now lands exactly on the part of the estimate that is optimistic.

**Claim before measuring:** At least as good as own_cost, i.e. damping the tail alone recovers the damping benefit without giving up the own-cost gain.

**Measured outcome:** Measured faster than own_cost on the full corpus, and the best configuration measured so far.

**Decision.**

Accepted. Best pooled result measured on this corpus: 1366.94, which is -6.78% against stock ECTD and -1.02% against AEFT.

The size of the gain is small (0.12% over own_cost) and on its own would not justify an entry. What justifies it is that the mechanism predicted the sign and the reason: damping should help once it is applied only to the estimated part. It does, and it helps at a self_weight where damping the whole tail was measured as slightly harmful. A 0.12% move in the predicted direction, with a mechanism that explains why the earlier measurement said otherwise, is worth more than a 0.12% move on its own.

Honest limit: 0.12% is close to the resolution of this corpus. The ordering against own_cost is consistent across the 282-instance stratified sweep and the 2094-instance full run, which is why it is accepted, but it should not be described as a large effect. It is a small correction that happens to be in the right direction for a stated reason.

Still open: the per-family picture is unchanged. This configuration beats AEFT on FFT, Genome, LIGO and Montage, and loses on GE (+1.54%) and LA (+2.86%). Those two families are where the remaining gain is, and they are a separate problem from the pooled score.

**Evidence:** `scripts/ectd_search.py full-corpus run, 2094 instances`; `scripts/ectd_search.py sweep, 282-instance stratified sample`

### `ectd_succ_own_g0p5` — ECTD rank with own-cost weight gamma=0.5, beta=0.5

**Status:** ACCEPTED  
**Kind:** algorithm

**Measured:** `v:ectd_succ_own_b0p5_g0p5` = 1360.64 pooled, -7.21% vs `ECTD`, -1.47% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

The winning successor rank uses a node base of mean_q oct[i][q], the tail only. But the scoring rule that won earlier established that the task's own cost deserves extra weight (self_weight = 2). The rank ignores that principle. This family applies it to the ordering:

base(i) = mean_q [ oct[i][q] + gamma * w[i][q] ] rank(i) = base(i) + beta * max_c ( edge(i,c) + rank(c) )

gamma = 0 reproduces the current best exactly, verified to == across 10 graphs. gamma = 1 makes the base the mean IOCT. gamma = 2 matches the scoring rule's double weight on own cost.

This also partly recovers what descendant_ranks had and the cheap OCT base lacks: descendant_ranks' DCT weight starts from min execution time, an own-cost quantity. gamma asks how much of that the rank needs.

**Claim before measuring:** Expected worse than gamma=0.

**Measured outcome:** Pooled 1360.64, better than gamma=0 (1362.58), -0.142%.

**Decision.**

Accepted. New best on the corpus: 1360.64, which is -0.142% against the previous best v:ectd_succ_max_0p5, -1.474% vs AEFT and -7.211% vs published ECTD. Still O(e p), so the complexity requirement holds.

My prediction was wrong. I predicted gamma=0.5 would be worse than gamma=0 and gamma=1 better. The measurement is the reverse: gamma=0.5 is best (1360.64), gamma=1 is second (1361.85), gamma=0 is third (1362.58). The reasoning that own cost should be weighted in the rank was right; my guess at the right magnitude was wrong. Recorded as-is.

The gamma curve has an interior optimum at 0.5: gamma=0 gives 1362.58, 0.5 gives 1360.64, 1 gives 1361.85, 2 gives 1370.25. gamma=2 collapsing sharply is informative: matching the scoring rule's self_weight of 2 in the rank is too much. The two mechanisms want different magnitudes.

The beta refinement at gamma=0 confirms 0.5 was the peak: 0.375 gives 1363.68 and 0.625 gives 1363.77, both worse than 1362.58. So beta=0.5 was not a lucky grid point.

Per family vs the previous best: Montage -0.39%, Genome +0.14%, LIGO -0.20%, FFT -0.29%, GE +0.26%, LA +0.08%. Instance-weighted over the three families carrying 91.4% of the corpus that is -0.157%, so the gain is on the bulk. GE regresses slightly here, but it remains far better than published ECTD, which was the original gap.

Strict wins 66 versus 26 for the previous best, so this one wins more outright as well as pooling better. That is a stronger result than the previous step, where pooled gain came with fewer strict wins.

### `ectd_succ_max_0p25` — ECTD successor accumulation (max, beta=0.25)

**Status:** ACCEPTED  
**Kind:** algorithm

**Measured:** `v:ectd_succ_max_0p25` = 1365.27 pooled, -6.90% vs `ECTD`, -1.14% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

The lam family varied how to collapse one OCT row by its LEVEL (max -> mean). The curve was monotone with the optimum at lam=1, so tail-level pessimism is not the mechanism. What descendant_ranks actually buys is downstream influence: a task with many important successors is urgent. That is the dimension lam never touched.

The node weight is still ECTD's own OCT table. beta controls how much successor influence propagates:

base(i)  = mean_q oct[i][q] max form:  rank(i) = base(i) + beta * max_c ( edge(i,c) + rank(c) ) sum form:  rank(i) = base(i) + beta * sum_c ( edge(i,c) + rank(c) )

The sum form double-counts shared successors. That is deliberate: it is O(e), not the O(e n/w) transitive closure, and it is the cheapest way to approximate the descendant count. Both forms are O(e p) to build the table plus O(e) to propagate, so both clear O(n^2 p).

**Claim before measuring:** Expected to beat descendant_ranks by restoring downstream influence.

**Measured outcome:** Pooled 1365.27, better than descendant_ranks 1366.94 (-0.122%).

**Decision.**

Rejected. Pooled 1365.27 against descendant_ranks 1366.94.

The max form has an interior optimum at beta=0.5; this setting is off that peak. The sum form is worse at every beta, which shows that double-counting shared successors is too crude an approximation to the distinct-descendant sum.

Kept in the registry so the shape of the curve is visible rather than only its winner.

**Evidence:** `docs/COMPLEXITY.md`

### `refactor_byte_scan` — Read the descendant bitmask by bytes instead of peeling set bits

**Status:** ACCEPTED  
**Kind:** refactor

**Equivalence:** `docs/equivalence/byte-scan-and-bisect.json`

Scope: Removes the per-set-bit walk from the rank. Does NOT remove the per-edge big-integer union, which is the other n^3/w term. ECTD is O(n^3/w + n^2 p) before this change and O(n^3/w + n^2 p) after it, so this is a constant-factor win and not a bound fix.

**Mechanism.** Why this should move the result, in algorithm terms.

descendant_ranks peeled one set bit at a time with `bits & -bits` and `bits ^= low`. Each of those touches the whole n-bit value, so one iteration costs O(n/w) word operations. The loop runs once per distinct descendant, which is Theta(n^2) over all tasks, so the walk was O(n^3/w).

The loop only accumulates a sum, so the order of visitation does not matter. Scanning the mask as bytes costs O(n/8) per task regardless of popcount, which is O(n^2/8) for the walk.

Equality is exact rather than approximate because both routines visit set bits in ascending order, so the floats are accumulated in the same order. That matters downstream: the rank feeds a heap key in ready_order and a ceil-to-a-tenth boundary in critical_path_weights, where a reordering could flip a tie and change the schedule.

**Claim before measuring:** Bit-identical ranks and bit-identical schedules; only the cost changes.

**Measured outcome:** 482 rank cases and 282 instances x 14 policies compared, zero differences. 400/400 synthetic graphs bit-identical under exact ==, not a tolerance.

**Decision.**

Accepted on proof, not on a benchmark. A refactor that changes no output cannot be judged by a quality delta, and does not need to be: it is judged by identity, which is a stronger claim.

Measured speedup on the rank phase alone: 3.4x at n=500 and 3.9x at n=4000 on sparse graphs, 2.4x at n=4000 on dense. Those are observations, not the justification. The justification is the equivalence report.

Scope, and this is the part that must not get lost: this removes one of two n^3/w terms. The rank after the change is O(e*n/w + n^2), and at the worst case e = Theta(n^2) that is still O(n^3/w). ECTD does not meet O(n^2 p) before this change and does not meet it after. An earlier version of this entry said the change made ECTD O(n^2 p) on sparse graphs, which conditioned a complexity claim on the input's density. That is not a bound and the claim has been withdrawn.

**Evidence:** `docs/equivalence/byte-scan-and-bisect.json`; `docs/COMPLEXITY.md`

### `refactor_calendar_bisect` — Locate the insertion gap by bisecting instead of scanning from zero

**Status:** ACCEPTED  
**Kind:** refactor

**Equivalence:** `docs/equivalence/byte-scan-and-bisect.json`

Scope: Removes a linear scan from placement. Placement was already inside O(n^2 p), so this is a low-order and constant-factor win, not a bound fix. It changes no exponent anywhere.

**Mechanism.** Why this should move the result, in algorithm terms.

earliest_slots walked every event on a processor from index 0 for every (task, processor) pair, and place located its insertion point with a linear `next(...)` over the calendar. Both were O(n) per call, so placement carried an O(n^2) term unrelated to the algorithm.

Events on one processor never overlap, so their start times and their finish times are both ascending. Two consequences:

In place, the insertion index is bisect_right over the start times, which returns the first index whose start is strictly greater, exactly what the linear `next(...)` returned.

In earliest_slots, any event finishing at or before the candidate is a no-op: its start is also <= candidate, so it cannot trigger the break and it cannot raise the candidate. Skipping them is equivalent to walking from index 0. bisect_right over the finishes finds the first event that can still matter, and the scan re-bisects whenever the candidate moves forward.

**Claim before measuring:** Bit-identical schedules; only the cost changes.

**Measured outcome:** 282 instances x 14 policies compared, zero differences, zero invalid schedules. The 23-test suite passes.

**Decision.**

Accepted on proof. Same reasoning as the byte-scan: identity is the claim, and the equivalence report is the evidence.

self.events stays a list of per-processor lists in the same order, because tests/test_suite.py:263 reads it directly. The bisect index is a parallel pair of lists updated at the single write site, so it cannot drift from the calendars.

Scope: this changes no exponent. It is worth having because placement is the phase that carries the O(n^2 p) term for every policy, so its constant factor is paid six times over on every benchmark run.

### `ectd_succ_max_2` — ECTD successor accumulation (max, beta=2)

**Status:** REJECTED  
**Kind:** algorithm

**Measured:** `v:ectd_succ_max_2` = 1370.01 pooled, -6.57% vs `ECTD`, -0.80% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

The lam family varied how to collapse one OCT row by its LEVEL (max -> mean). The curve was monotone with the optimum at lam=1, so tail-level pessimism is not the mechanism. What descendant_ranks actually buys is downstream influence: a task with many important successors is urgent. That is the dimension lam never touched.

The node weight is still ECTD's own OCT table. beta controls how much successor influence propagates:

base(i)  = mean_q oct[i][q] max form:  rank(i) = base(i) + beta * max_c ( edge(i,c) + rank(c) ) sum form:  rank(i) = base(i) + beta * sum_c ( edge(i,c) + rank(c) )

The sum form double-counts shared successors. That is deliberate: it is O(e), not the O(e n/w) transitive closure, and it is the cheapest way to approximate the descendant count. Both forms are O(e p) to build the table plus O(e) to propagate, so both clear O(n^2 p).

**Measured outcome:** Pooled 1370.01, worse than descendant_ranks 1366.94 (+0.225%).

**Decision.**

Rejected. Pooled 1370.01 against descendant_ranks 1366.94.

The max form has an interior optimum at beta=0.5; this setting is off that peak. The sum form is worse at every beta, which shows that double-counting shared successors is too crude an approximation to the distinct-descendant sum.

Kept in the registry so the shape of the curve is visible rather than only its winner.

### `ectd_lam_0` — ECTD rank with lam = 0: pure max of the OCT row

**Status:** REJECTED  
**Kind:** algorithm

**Measured:** `v:ectd_lam_0` = 1375.76 pooled, -6.18% vs `ECTD`, -0.38% vs `AEFT`

**Mechanism.** Why this should move the result, in algorithm terms.

ECTD's optimistic cost table is per processor: oct[i][q] is the best-case cost of everything after task i, given i runs on q. Ordering tasks requires collapsing that row to one number, and the collapse is a choice no other algorithm in the suite makes explicitly:

rank_lam(i) = max_q oct[i][q] + lam * (mean_q oct[i][q] - max_q oct[i][q])

lam = 0 is the max: assume the tail runs on its worst processor, so a task whose tail is expensive somewhere is urgent. lam = 1 is the mean, which is what AEFT and IPPTS effectively use and which measured 1.0% worse than descendant_ranks. lam > 1 goes below the mean toward the min.

So lam is one knob on how much per-processor pessimism the ordering keeps. The claim is that lam < 1 orders better than the mean, because a task that is expensive on its worst processor is more urgent than its average suggests.

This is deliberately not an imported rank. The v:rank_* variants take another algorithm's priority order wholesale, which solves the complexity problem but leaves ECTD with no contribution of its own in the ordering. Here the table and the parameter are both ECTD's.

**Claim before measuring:** lam = 0 is expected worse than descendant_ranks.

**Measured outcome:** Pooled 1375.76, worse than descendant_ranks 1366.94.

**Decision.**

Rejected. The curve is monotone in lam: lam=1 is the best of the family and every step toward the max is worse. lam=1 is itself 0.207% worse than descendant_ranks, so the family does not reach the thing it was meant to replace.

The mechanism is falsified. The claim was that a task expensive on its worst processor is more urgent than its average suggests, so lam < 1 should beat the mean. It does not. Per-processor pessimism in the row collapse is not what descendant_ranks buys.

What it did get right: every lam beats descendant_ranks on GE and LA by 1.9-3.0%, and pays for it on Montage, Genome and LIGO. Same trade as the AEFT-ordering swap, just smaller. That is recorded here so the next rank candidate is not judged on GE and LA alone.

Kept in the registry as a rejection, not deleted. This is the record of a mechanism that was argued, predicted, measured and falsified.

## How to add an entry

An **algorithm** entry changes what the policy computes, so it is judged on
quality and needs a measured delta:

1. Add the variant to `scripts/ectd_variants.py` (or a new module) and give
   it a `v:` prefixed name so it cannot be mistaken for a published policy.
2. Add an entry to `registry.json` with `status: "proposed"`, the mechanism,
   and the claim. A proposed entry cannot be merged.
3. Run the ablation workflow. It scores every variant on the real corpus.
4. Run `python3 scripts/render_optimizations.py`. If the artifact contradicts
   the claim, it fails. Fix the claim or the code, not the document.
5. Set the status to `accepted`, `rejected` or `inconclusive` and record the
   reasoning in `decision`. Rejected entries stay: they are the record of
   what has already been ruled out.

A **refactor** entry changes how the policy is computed but not what it
computes, so it is judged on identity and needs no delta:

1. Set `kind: "refactor"` and give an `equivalence` block naming a report
   committed to the tree, plus a `scope` line saying what the change does
   and does not buy. A refactor that claims a bound improvement it does not
   deliver is the failure mode this field exists to prevent.
2. Run the equivalence workflow. It writes `equivalence-report.json`.
3. Commit that report to the path the entry names. The gate requires the
   file to exist and to record `verdict: EQUIVALENT` with no failures.

The gate rejects an algorithm entry with no `code.policy_key` and a refactor
entry with no committed report. Neither can pass on prose alone.
